# WP41 maintainer guide: JupyterLite course platform

This is the infrastructure contract for migrating Exercises 1 and 3-12 the
same way Exercise 2 was migrated. It assumes you have read
`WPs/WP41_REVISED_JUPYTERLITE_COURSE_PLATFORM_AND_ACTIVE_EXERCISE_2.md` and
`WPs/reports/WP41_REPORT.md`.

## 1. Architecture in one paragraph

The Jupyter Book hub (`book/`) still owns Introduction, Syllabus, and
Contents. Each migrated exercise's *canonical* Jupyter Book page
(`book/chapters/chapter_NN/exercise_NN.ipynb`) becomes a short transition
page that links to a JupyterLite notebook. The real lesson lives once, as a
generated notebook, in `book/lite/files/exercise_NN.ipynb`; the exact same
generated content is also published as the downloadable/Colab copy at
`book/downloads/chapter_NN/exercise_NN_portable.ipynb`. JupyterLite is built
as a separate step, straight into `book/_build/html/lite/`, after the
Jupyter Book build -- it never overwrites the book hub.

## 2. Adding or updating the exercise manifest

Edit `book/config/exercise_manifest.json`. Each entry needs: `number`,
`title`, `migrationState` (`"legacy"` or `"migrated"`), `legacyStaticPagePath`,
`templateNotebookPath`, `browserWorkingCopyName`, `liteUrl`,
`templateVersion`, `dataAssets`, `extraPackages`, `fallbackDownloadablePath`.
Migrated entries must set every Lite-specific field; legacy entries must
leave them `null` (enforced by `tests/test_exercise_manifest.py`). Bump
`templateVersion` whenever you republish a migrated exercise's template with
content changes students may already have started (see section 5).

## 3. Declaring packages and data

**Packages**: the common set (`numpy`, `pandas`, `scikit-learn`,
`matplotlib`, `ipywidgets`) is preloaded for every notebook via
`book/lite/overrides.json`'s `loadPyodideOptions.packages` -- this works
because Pyodide ships prebuilt wheels for all of them. A package with **no**
prebuilt Pyodide wheel (like `ipywidgets` itself, or `plotly` if a future
exercise wants it) cannot go in that list; instead, fetch it once via
`micropip` inside the notebook's own collapsed setup cell, guarded by
`if sys.platform == "emscripten":` so local Jupyter/Colab (which already
have it installed) skip the fetch entirely. See
`scripts/generate_exercise_02_notebook.py`'s `SETUP_SOURCE_TEMPLATE` for the
exact pattern. Check whether a candidate package has a Pyodide wheel before
assuming either path: `curl -s https://cdn.jsdelivr.net/pyodide/v<version>/full/pyodide-lock.json | grep -i <package>` (get `<version>` from
`jupyterlite_pyodide_kernel.constants.PYODIDE_VERSION` in the pinned venv).

**Data**: never point a JupyterLite notebook at a live GitHub URL as its
*only* source -- it must not require Git access, a token, or repository
visibility. Export a same-origin static asset instead:
`scripts/export_abide_lite_data.py` is the model to copy (network `--write`
regenerates from the pinned source; offline `--check` validates the
committed file's checksum, schema, participant count, and predictor count
against a sidecar `*.manifest.json`). Put the exported file(s) under
`book/lite/files/data/`. Keep exports slim -- only the columns a notebook
actually needs, not the full raw table.

**Portability across JupyterLite, downloaded-local-Jupyter, and Colab**:
put the "where's my data" decision in exactly one small helper function
inside the collapsed setup cell (see `load_abide_age_brain_table()` in
`scripts/generate_exercise_02_notebook.py`): try the same-origin file first
(works in JupyterLite, and in a full local checkout); fall back to the
pinned, checksummed public URL otherwise (works for a bare downloaded
`.ipynb` or Colab, neither of which has the sibling data file -- the
**Download my notebook** contract only covers the `.ipynb` itself). Both
paths must return identically ordered columns, or downstream code that
prints "the first N features" or pairs feature names with coefficients will
silently disagree between environments. Verify this with a same-values
check like `tests/test_exercise_02_reference_execution.py` does, not by
inspection.

## 4. Generating the template and portable notebooks

Follow `scripts/generate_exercise_02_notebook.py`'s shape: one Python module
is the single authoritative source. Represent every "YOUR CODE HERE"
activity as a `Blank(student_source, reference_source, cell_id, tags)` pair;
`--student` renders the starter side into both
`book/lite/files/exercise_NN.ipynb` and
`book/downloads/chapter_NN/exercise_NN_portable.ipynb` (literally the same
generated bytes -- there is no separate MyST-directive-rewriting step like
the legacy `scripts/build_portable_notebook.py` pipeline uses, because a
JupyterLite-native notebook has no MyST directives or iframes to rewrite in
the first place); `--reference` renders the solved side into
`scripts/reference_notebooks/exercise_NN_reference.ipynb`, used only by
tests, never published. `--check` (no writes) is what CI should run;
`--write` regenerates. Never hand-edit any of the three generated `.ipynb`
files directly -- edit the generator and regenerate.

Also generate the transition page from a script
(`scripts/generate_exercise_02_transition_page.py`): keep its H1 identical
to the notebook's title (the book Contents page's `{tableofcontents}`
listing reads it from there) and give it nothing but a link to the
JupyterLite URL and the portable download -- no re-created analysis content.

When you add a reference plot image (an "approved current result" a student
compares their own plot against), render it with a small dedicated script
(see `scripts/render_exercise_02_reference_plot.py`) from the same committed
data export, and embed it as a base64 `data:image/png` URI directly in a
markdown cell -- never as a separate linked file, which would break for a
downloaded/Colab copy.

## 5. Personal working-copy routing, autosave, and template versioning

JupyterLite's contents manager already layers browser storage (IndexedDB)
over the static served files: the first open seeds from the static
template, and every save afterward reads/writes IndexedDB -- students get a
personal working copy and autosave for free, with no extra code. This also
means a republished template with *edited* content will **not** silently
overwrite a student's already-started browser copy (they keep seeing their
IndexedDB version) -- but it also means they will not automatically see
your fix either. WP41 did not need to solve template-version-changed
prompting because Exercise 2 is a first migration, not a republish; a real
future republish should compare the open document's
`metadata.wp41.templateVersion` against the manifest's `templateVersion`
and, if they differ, offer (do not force) the reset-from-template flow the
toolbar already has, after warning the student and pointing at
**Download my notebook** first.

## 6. Adding Back, Download, Reset, and autosave behavior

Reuse `book/lite/extensions/course-toolbar/` as-is -- it is generic (derives
both the Contents-page URL and the per-notebook template URL from
`window.location`, not from any per-exercise configuration) and is wired
into every JupyterLite notebook automatically via
`book/lite/jupyter_lite_config.json`'s `federated_extensions`. You do not
need to touch it to migrate another exercise. If you do change it: rebuild
with `cd book/lite/extensions/course-toolbar && npx tsc && jupyter
labextension build --development True .` (needs the repo `.venv`
activated), then rebuild JupyterLite.

## 7. Writing portability-safe code

- Never `import` a JupyterLite-only API (`js`, `pyodide_js`, browser DOM
  bindings) in a student-facing cell -- only standard `ipywidgets` +
  Matplotlib (or Plotly, if its Pyodide wheel exists and you add it to
  `overrides.json`).
- Never rely on a specific label/order from `sys.platform` beyond the exact
  `"emscripten"` check already established.
- Keep every "helper" cell (data loading, question-checking widgets)
  collapsed but never hidden-and-unexplained: a student who expands it must
  be able to read and run it, per section 4.5's "collapsed is fine, an
  opaque black box is not."
- A blank student cell must never define a variable a *different,
  independent* later section requires without a graceful existence check
  (see Section 5's check cell in Exercise 2 for the pattern) -- one
  incomplete answer must not cascade into unrelated failures.

## 8. Adding focused browser and notebook tests

Structural/offline checks (no kernel, no browser) belong in
`tests/test_exercise_NN_lite_notebook.py`, modeled on
`tests/test_exercise_02_lite_notebook.py`: YOUR CODE HERE tasks present, no
`raise NotImplementedError`, editable answer cells present, checked
questions keyed, student/portable/reference structurally synchronized via
`--check` on the generator.

Numeric/executed checks belong in
`tests/test_exercise_NN_reference_execution.py`, modeled on
`tests/test_exercise_02_reference_execution.py`: execute the reference
notebook's cell sources directly (via `ast.PyCF_ALLOW_TOP_LEVEL_AWAIT` +
`asyncio`, not `jupyter execute`/nbclient's `.execute()`) and assert the
established numbers. **Do not** use `jupyter execute`/plain `nbclient`
against a notebook containing an ipywidgets `Output()` used as a context
manager: it was found to hang indefinitely with no real frontend attached
to acknowledge the widget comm handshake. This is specific to headless,
frontend-less execution -- the same pattern works fine both in a real
browser (verified against the actual JupyterLite build with Playwright) and
in a plain Jupyter Book notebook that never touches `Output()`.

Browser/platform checks belong in
`interactive/e2e-book/exercise-NN-lite.spec.ts`, modeled on
`exercise-02-lite.spec.ts`. Three non-obvious things every such spec needs:
1. **Scroll before you query.** The notebook's cell list is virtualized
   ("windowed"): a cell far off screen is not in the DOM. Scroll the
   `.jp-WindowedPanel-outer` container to the right fraction first.
2. **Use the toolbar Save button, not Ctrl+S; clear cells with repeated
   Backspace, not Ctrl+A.** This machine (and typical CI images) report a
   Mac-like platform to JupyterLab's keybinding layer, which then expects
   Cmd (Meta) for "Accel"-bound commands; Ctrl+S/Ctrl+A silently do nothing.
3. **ipywidgets 8's `IntSlider` is not a native `<input type=range>`.** It
   renders via noUiSlider; the keyboard-operable, focusable element is
   `.noUi-handle` inside `.widget-slider`.

Before running: `jupyter-book build book`, then
`jupyter lite build --config book/lite/jupyter_lite_config.json --lite-dir
book/lite --output-dir book/_build/html/lite`. CI does not yet run the
JupyterLite build step automatically (wiring that into
`.github/workflows/deploy.yml`, and everything after, is deliberately out of
WP41's scope -- see "Deviations" in `WPs/reports/WP41_REPORT.md`).

## 9. Preserving model-result audits

Before changing a migrated exercise's recipe, split, or model settings,
capture the currently-established numbers (read them from the existing
notebook's executed outputs, or recompute from the committed data export)
and add/extend a numeric-integrity test asserting them, the way
`tests/test_exercise_02_reference_execution.py` asserts R²=0.469 etc. A
change that legitimately alters a number must update both the notebook and
that test in the same change, with the reason stated in the commit message
-- never let a test go stale to "fix" a result drift.

## 10. Retiring an old static exercise only after parity is verified

Do not delete or blank a `book/chapters/chapter_NN/exercise_NN.ipynb`
canonical page until:
1. the new `book/lite/files/exercise_NN.ipynb` passes its structural test
   suite and its reference notebook passes its numeric-integrity suite;
2. `interactive/e2e-book/exercise-NN-lite.spec.ts` passes against a real
   combined build;
3. the manifest's entry for that exercise is flipped to
   `"migrationState": "migrated"` and its Lite fields filled in
   (`tests/test_exercise_manifest.py` enforces the schema);
4. any exercise-content-audit tests that read the *old* canonical page
   (search `tests/` for the exercise's chapter path) are updated to read the
   new locations instead -- WP41 had to update five such files
   (`test_notebook_opening_structure.py`, `test_think_first_shared_class.py`,
   `test_wp19_content_audit.py`, `test_wp24_content_audit.py`,
   `test_wp25_content_audit.py`) because they cross-referenced Exercise 2's
   old implementation details; expect the same for the next migration.

Only then replace the canonical page with a transition page. Never leave
two divergent copies of the same lesson content live at once.
