## Educational contract

Open with one short invitation: each case contains code that runs and produces a plausible result, but its conclusion may be invalid or its model unnecessarily poor. The recurring flow is **run → diagnose → repair or compare → inspect the consequence**. Use neutral subsection headings so titles do not reveal the mistake before students inspect the code. The intentionally flawed cells must run without red tracebacks. Label contaminated or otherwise invalid results clearly *after* the diagnosis so they cannot be mistaken for legitimate benchmarks.

Aim for five required cases and one short closing challenge. Keep each example concise and runnable, with a checked understanding question and a student correction or supplied comparison. Use the established same-origin ABIDE-II data where it makes sense; use small, deterministic synthetic data when it explains a mechanism more clearly, and label it as synthetic. Make cases independent: an unfinished blank must not break later cases or widgets. On the untouched template, Run All should produce helpful incomplete-task notices and no cascade of errors.

## Required cases

| Case | Runnable flawed analysis | Student action and valid comparison |
|---|---|---|
| 1. Preparing predictors | Fit `SimpleImputer` and/or `StandardScaler` on the whole dataset before the split or cross-validation. | Ask what information crossed the boundary. Students repair the workflow with preprocessing fitted within training data/folds, preferably in a `Pipeline`. Show an observable change in a learned preprocessing statistic, such as training-only versus whole-data median/mean. Do not promise a large score difference. |
| 2. Two components | Include `y` itself among PCA inputs, then use the resulting components to predict `y`, including on held-out rows. The bad code must run and show a striking but invalid result. | Ask what would be needed to transform a genuinely new participant. Students create a predictor-only matrix, fit PCA on training predictors, and transform held-out predictors. Use a small synthetic regression example if needed for a reliable contrast. |
| 3. Picking a tree | Fit a predefined list of tree depths and select the depth with the lowest training MSE. | Students plot training and validation MSE and select by validation performance. Reserve an untouched test partition for the interactive comparison. Use a defensible prespecified ABIDE split/grid if the pattern is clear; otherwise a clearly labeled synthetic nonlinear example. Do not search many seeds for an attractive result. |
| 4. A high-accuracy classifier | On a reproducible synthetic 95:5 classification task, always predict the majority class and report accuracy alone. | Supply a confusion matrix. Students inspect or calculate sensitivity, specificity, precision (if defined), and balanced accuracy, then answer a concrete screening/follow-up question. Explain why precision alone or specificity alone can omit important errors. Handle undefined precision explicitly without warning; no metric is universally best. |
| 5. Many rows per participant | Split repeated observations/epochs at random by row, so a participant appears in training and test data. | Students detect participant-ID overlap and repair the split with `GroupShuffleSplit` or another group-aware method. Compare results with the row split. Use small synthetic participant-pattern data, clearly labeled; do not imply that this course's ABIDE table contains repeated epochs. The evaluation target is performance on new participants. |
| 6. Closing challenge | Try parameter settings on the test set, choose the best test score, and call it an untouched evaluation. | One compact example and a checked question identify when the test set began guiding the choice. After the question, give the corrected train/validation-or-CV/test-once workflow in prose; no long nested-CV computation. |

Four meaningful student repair blanks (Cases 1, 2, 3, 5) are the target. Other cases can focus on interpretation. Give required output names only where a later check needs them. Graceful checks should accept equivalent correct approaches when feasible and avoid blocking later material. Do not claim a structural check proves every arbitrary solution free of leakage.

## Two notebook-native interactive activities

1. **After Case 2 — “A result that knows the answer.”** A native `ipywidgets` toggle compares contaminated PCA and predictor-only PCA on the same fixed held-out observations. Display true-versus-predicted scatter plots with the same axis range, diagonal guide, and clearly labeled `R²`. The invalid path may look excellent because it is handed held-out `y` during transformation; the valid path must never use held-out `y` for fitting, transforming, or prediction. Supply self-contained demonstration outputs so the widget works even if the student leaves the repair blank. Include a checked question about deployment when a new participant's target is unknown.
2. **After Case 3 — “Which tree gets deployed?”** A native toggle chooses depth by lowest training MSE or lowest validation MSE on the same predefined grid and split. Mark the depth on train/validation curves and show its predictions on one untouched test set at fixed plotting ranges. Test MSE or R² may be shown for context but must not influence selection. The lesson is that training-based selection may genuinely generalize worse; do not call a valid held-out score “falsely pessimistic.” Keep the toggle responsive in Pyodide by using small fixed fits or precomputed results.

Check label wrapping, visible plot changes, fixed axes, responsive controls, and lack of red runtime warnings in the real JupyterLite preview. No iframe or new standalone widget app.

## Questions, hints, and pace

- Use approximately 6–8 substantive checked questions across the cases. Mix single choice and select-all where appropriate. Ask about diagnosis, consequence, and repair, not just the section title. Use `show_question(id)` with keys in hidden setup; never display `correct_index` or `correct_indices` in visible cells. Deterministically shuffle options once per question except when their order is semantically meaningful. Long answers must wrap in desktop and narrow browser views.
- Audit the **generated student notebook** for solution leakage. Do not put a complete repaired solution in commented `# YOUR CODE HERE` lines. A short hint such as “consider `Pipeline`” or “split by participant ID,” plus necessary output names, is fine. Keep instructor notes and code out of student-facing cells.
- Be precise about the distinct failures: Case 1 learns preprocessing statistics from held-out observations; Case 2 directly inserts the target into features; Case 3 selects a model by training scores; Case 5 evaluates on familiar participants. A prettier score alone does not establish which information leaked.
- Keep prose short. Credit the course data and distinguish synthetic demonstrations from ABIDE observations. Follow current browser and portable-import conventions. Do not ask students to install from the repository or `requirements.txt`.
