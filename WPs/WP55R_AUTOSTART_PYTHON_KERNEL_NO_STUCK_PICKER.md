## Required behavior and implementation

For Exercises 1–9, the JupyterLite notebook should **automatically select and start its actual Python (Pyodide) kernel when the kernel is ready**, without showing an initial kernel-choice modal. An explicit user request to change the kernel later may still show the normal selector. During a slow first load, display a nonblocking, informative startup state; after a genuine load/registration failure, give a clear retry/error path that does not erase notebook edits. The student should not need to refresh or interact with a frozen `No Kernel` dialog to run a cell.

Investigate the **dialog's lifecycle and timing**, not just whether `sessionContext.session?.kernel` becomes non-null eventually. A post-open 30-second recovery can start a kernel while a modal that opened earlier remains stuck in front of the notebook; a fix that only starts Python in the background is incomplete. Inspect how this build creates `SessionContext`, gets its kernel preference, chooses a default, opens `SessionContextDialogs.selectKernel`, and registers Pyodide specs. Work through supported JupyterLab/JupyterLite extension APIs and the app's existing toolbar integration. In the current build the published notebook metadata asks for `python3` while JupyterLite's registered kernel/default is `python`; resolve that mismatch in the **browser experience** if it contributes. Preserve downloaded/Colab/local Jupyter compatibility: do not blindly change every portable notebook's kernelspec to `python` without verifying it works in those environments. Ensure the default-kernel choice happens early enough to prevent the unwanted modal, or actively resolve/cancel an already-open initial dialog safely once Python becomes available. Avoid blind fixed sleeps, repeated competing `changeKernel()` calls, unconditional page reloads, and suppressing all future user-requested kernel dialogs.

If the exact screenshot state cannot be reproduced on the current release, use deterministic fault injection in a **local test build** (for example delay kernel-spec registration/extension loading) to exercise the initial dialog/race path and prove the pre-fix behavior versus the fixed behavior. Also investigate whether a browser's cached old shell/service worker can mix release versions; if that is the cause, use safe version-aware refresh/recovery without deleting student notebook data. State precisely which mechanism was proved and which remains an inference. If the screenshot is conclusively from an earlier build and the current build already handles this state, provide that evidence and a safe way for the author to refresh the shell while preserving edits; do not ship an unnecessary speculative patch merely to make a new commit.
